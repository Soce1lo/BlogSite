# Vault 与 BlogSite 协作架构设计

## 背景

当前 BlogSite 是 Obsidian KnowledgeVault 的公开输出端。Vault 负责知识生产、私人上下文、正文编辑和发布授权；BlogSite 负责公开副本、网页展示、路由、交互、部署和线上验证。

现有协作已经具备真实 Vault 只读同步、`blog` / `notes` / `projects` 三类内容、双链和资源转换、发布检查、manifest、GitHub Pages 部署及 live verification。随着 BlogSite 引入 Growth Output Log、长期主题和 `publish_kind`，网站展示需求开始反向提出新的公开元数据要求；与此同时，Vault 的发布模板、字段说明和发布 MOC 没有自动吸收全部新语义，出现了契约实现、作者模板和历史 manifest 不完全同步的现象。

未来还可能同时发生两类重构：

- 更换 Astro 或整体替换网站发布框架；
- 改变 Vault 的目录、知识组织方式、Markdown/frontmatter 结构，甚至替换知识来源系统。

本设计为当前协作建立稳定边界，并保证两个系统未来都可替换。

## 已确认决定

采用以下总体模型：

> 单向内容数据流、双向设计反馈、框架无关发布协议、两端可替换适配器。

同时确认：

1. 所有发布契约模型、版本定义、机器 schema、示例和兼容规则都维护在当前 BlogSite 仓库。
2. 知识来源层不复制契约模型，只在实际来源目录内写明作者和 agent 需要遵守的局部约定。
3. 网站的设计反馈只能影响公开表达层；未经明确授权，不得自动改变 Vault 的正式知识结构、私人工作流或发布状态。
4. 当前 `blog` / `notes` / `projects` 是发布协议 V1 的分类，不是永久枚举。
5. 未来可以在同一迁移项目中同时改变 Vault 与网站组织方式，但技术上必须分阶段切换并分别保留回滚点。

## 目标

1. 明确 Vault、发布协议、适配器和网站产品层的责任边界。
2. 将发布接口从 Astro schema 和 Vault 目录结构中解耦。
3. 允许 BlogSite 提出新的公开语义，又不让网站反向控制知识库。
4. 允许 Vault 改目录、改组织模型或更换存储系统，而不必重写网站产品逻辑。
5. 允许 BlogSite 更换框架、导航或路由，而不必批量改写 Vault 正文。
6. 通过版本化协议、manifest、兼容期和重定向支持未来迁移。
7. 保持当前真实 Vault 只读、CI 不读取 Vault、发布需人工授权的安全边界。

## 非目标

- 不建立 Vault 与 BlogSite 的双向内容同步。
- 不让 BlogSite 自动更新 Vault frontmatter 或正文。
- 不把当前完整 Vault、私人附件或本机配置提交到 BlogSite。
- 不立即建立第三个契约仓库或共享 npm 包。
- 不立即实现多个发布框架或复杂插件系统。
- 不为了未来可能的迁移现在就批量重写所有 Vault 内容。
- 不把 `60-Publish/`、PAREA 目录或 Astro collection 固化为永久协议。

## 架构原则

### 单向数据流

公开正文只从知识来源流向发布端：

```text
知识来源
  -> 来源适配器
  -> 框架无关公开内容记录
  -> 发布适配器
  -> 网站框架
  -> 部署结果
```

BlogSite 到 Vault 的反向路径只允许产生：

- 新的契约字段提案；
- 作者模板或目录局部约定的更新需求；
- 某篇公开稿需要补充元数据的编辑建议；
- 发布失败、隐私风险或兼容问题报告。

反向路径不得自动写入真实知识来源。

### 两端可替换

Obsidian 和 Astro 都是当前实现，不是长期协议本身：

- 知识来源变化时替换来源适配器；
- 发布框架变化时替换发布适配器；
- 公开内容领域模型和历史身份在两种迁移中保持稳定。

### 目录不是协议

Vault 内的 `10-Notes/`、`20-Projects/`、`60-Publish/`、`70-LLM-Wiki/` 等目录属于当前知识工作流。发布资格由显式发布元数据和人工授权决定，不由源文件路径决定。

`60-Publish/` 当前继续作为编辑、匿名化、策划和授权工作区，但来源适配器不得把它当作永久唯一入口。

### 网站导航不是内容本体

当前 `blog` / `notes` / `projects` 同时承担 V1 分类和路由提示。它们不得再隐含 Vault 目录。未来网站可以把相同公开内容映射为新的导航、栏目或路径，而无需移动源文件。

## 分层职责

### 知识来源层

当前由 Obsidian Vault 承担，负责：

- 私人输入、Daily、正式知识笔记、项目资料和 LLM 派生层；
- 公开正文及其来源关系；
- 匿名化和私人上下文清理；
- `draft` 到 `published` 的人工授权；
- 标题、摘要、内容语义、主题、系列和可见性；
- LLM Wiki 到正式笔记或公开稿的人工 promote。

知识来源层只在实际发布来源目录中保留局部协作约定，例如：

- 哪些字段由作者填写；
- 何时允许设置 `published`；
- 哪些内容禁止公开；
- 如何引用 BlogSite 中的权威契约位置；
- 目录内 agent 可以和不可以做什么。

这些局部约定不得复制完整 schema、枚举或版本兼容逻辑。契约变化时，知识来源目录只更新使用说明和契约版本引用。

### 来源适配器

来源适配器负责把当前知识存储解释为统一记录：

- 发现带有发布元数据的候选内容；
- 解析 flat YAML、Markdown、Wikilinks 和本地资源；
- 将 Vault 字段映射到框架无关领域模型；
- 记录相对来源路径作为 provenance；
- 拒绝私人、Daily、未授权、字段非法或路径泄漏内容；
- 保证读取过程不修改真实 Vault。

Vault 改目录时只调整发现规则或映射。Markdown/frontmatter 被替换时，新增或替换来源适配器。

### 公开内容领域模型

公开内容领域模型是稳定核心，表达：

- 公开内容的稳定身份；
- 契约版本；
- 正文、标题、摘要和资源；
- 发布状态和可见性；
- 内容分类、输出语义、主题、系列和时间；
- 来源 provenance；
- slug、最终 URL 和重定向关系；
- warnings 和内容摘要指纹。

该模型不包含 Astro layout、collection loader、Obsidian 插件状态或 Vault 物理目录要求。

### 发布适配器

当前 Astro 发布适配器负责：

- 将领域记录转换为 `src/content/{blog,notes,projects}` Markdown；
- 生成 Astro 所需 `pubDate`、`draft`、`visibility`、`outputKind` 等字段；
- 复制公开资源；
- 生成目标 URL；
- 生成发布 manifest 和同步报告；
- 保留 `managedBy: vault-sync` ownership。

未来 Hugo、Next.js 或其他实现通过新的发布适配器消费相同领域记录。

### 网站产品层

网站产品层负责：

- 品牌、NOW、精选内容和长期主题；
- 首页、导航、搜索、RSS、SEO 和视觉系统；
- 路由、重定向、GitHub Pages base path 和部署；
- 将公开领域字段组合成读者可见的信息架构。

人工公开 Profile 继续由 BlogSite 维护，不从私人 Daily、任务或 git 状态自动推导。

## 契约权威位置

所有契约模型集中在 BlogSite 根级、框架中立的目录。建议实施位置：

```text
contracts/
└── publishing/
    └── v1/
        ├── contract.md
        ├── schema.json
        └── examples/
```

权威关系如下：

| 位置 | 角色 | 是否权威 |
| --- | --- | --- |
| `contracts/publishing/` | 协议、版本、schema、枚举、兼容规则 | 是 |
| Vault 来源目录局部约定 | 作者和 agent 的使用说明、契约引用 | 否 |
| Vault 发布模板 | 可选的作者填写辅助；只能引用契约 | 否 |
| Vault 发布 MOC | 私人策划和状态视图；不承载契约 | 否 |
| 来源适配器 | 协议输入实现 | 否，必须符合契约 |
| Astro content schema | 当前发布适配器输出约束 | 否 |
| publish manifest | 一次发布的执行证据 | 否 |

更换网站仓库或框架时，`contracts/`、公开身份基线、历史 manifest 和重定向记录必须作为显式迁移资产一起带走。

## 发布协议 V1

当前已实现 V1 的作者字段、必填与可选关系、枚举、默认行为、字段依赖和示例，统一以 [`contracts/publishing/v1/`](../../../contracts/publishing/v1/) 中的 `contract.md`、`schema.json` 和 `examples/` 为准。本架构文档只保留系统分层、责任边界和未来迁移设计，不再复制当前契约模型。

在责任边界上，V1 元数据只描述公开分类、路由候选、授权状态和展示语义，不代表 Vault 目录，也不得由 BlogSite 自动改写。稳定公开身份仍是未来迁移问题，不应把当前 URL 候选误当作永久身份。

### 未来建议字段

以下字段仅是未来协议演进建议，不是当前 V1 schema、来源适配器或发布流程已经实现或要求的字段：

- `publish_contract: v1`：声明来源内容遵守的协议版本。
- `publish_id`：与文件名、路径、标题和 slug 无关的稳定公开身份。

现有公开内容不要求在设计落地前批量改写。实施时为现有公开文章建立身份基线；新公开内容在过渡期结束后必须拥有 `publish_id`。

### 发布适配器生成字段

当前 Astro 输出字段属于发布适配器实现，不是 Vault 全局知识模型或 V1 来源字段。其精确约束由 Astro content schema 与同步器负责，架构层只要求它们可从权威契约记录确定性生成，并保留来源、授权状态和托管 ownership。

## 变更归属

| 变更类型 | 发起位置 | Vault 影响 | BlogSite 影响 |
| --- | --- | --- | --- |
| 颜色、字体、布局、交互 | 网站产品层 | 无 | 修改页面和样式 |
| NOW、精选、首页文案 | 网站产品层 | 无 | 修改公开 Profile |
| 使用已有 topic/series 组织页面 | 网站产品层 | 无 | 修改聚合和展示 |
| 新增可选公开语义字段 | 发布协议 | 更新局部约定和未来内容 | 更新契约、适配器、schema、测试 |
| 正文、摘要、状态或可见性 | 知识来源层 | 修改源内容 | 重新同步 |
| Vault 目录和内部组织调整 | 知识来源层 | 迁移来源 | 通常只调整来源适配器 |
| 网站栏目、导航或路由调整 | 网站产品层 | 通常无 | 更新映射和重定向 |
| 删除字段或修改字段语义 | 新协议版本 | 迁移公开来源 | 双版本适配和兼容验证 |
| 同时重构两端 | 统一迁移项目 | 分阶段迁移 | 并行建设后切换 |

## 协作流程

### 从知识来源发布新内容

```text
捕捉或研究
  -> 正式知识加工
  -> 发布 MOC 策划
  -> 形成公开稿
  -> 设置 draft
  -> preview sync
  -> 人工审阅
  -> 明确授权 published
  -> formal sync
  -> test/check/build
  -> 部署和 live verification
```

LLM Wiki 内容必须先经人工 promote，不能直接成为公开源。

### BlogSite 提出反向需求

1. 先判断需求能否由已有公开数据推导。
2. 能推导时只修改 BlogSite。
3. 不能推导时提出新的契约字段或语义。
4. 新字段优先保持可选并提供默认值。
5. 先更新 BlogSite 中的权威契约、来源适配器、发布适配器和测试。
6. 再更新 Vault 来源目录局部约定、模板和发布 MOC。
7. 只在编辑相关公开稿时补字段，不机械改写全库。

### 协议变更

使用“扩展—迁移—收缩”顺序：

1. 发布端先同时接受旧字段和新字段。
2. 来源目录约定和模板开始产生新格式。
3. 逐步迁移现有公开内容。
4. manifest 验证全部公开身份、状态和 URL。
5. 保留至少一个完整发布兼容周期。
6. 最后才移除旧字段支持。

新增可选字段、增加默认值或增加非破坏性枚举可以保留在 V1。删除字段、改变字段含义、改变默认公开行为或让旧内容无法解析时必须发布 V2。

## 同时迁移 Vault 与网站

知识组织和网站组织可以在同一迁移项目中统一设计，但必须按以下顺序技术落地：

1. 冻结现有公开内容清单、`publish_id`、slug 和 URL。
2. 定义协议 V2 和 V1 到 V2 的映射。
3. 来源适配器同时识别新旧来源结构。
4. 迁移知识来源，同时保持旧网站可构建。
5. 新发布适配器消费相同领域记录。
6. 并行生成新旧 manifest。
7. 比较内容数量、身份、状态、摘要、资源和 URL。
8. 部署新网站并建立重定向。
9. 观察一个稳定周期。
10. 移除旧来源适配器、旧发布适配器和旧字段支持。

业务上同时设计，技术上保留两个独立回滚点：

- 知识来源可回滚到迁移前组织；
- 网站可回滚到原框架和原路由。

## 错误处理

### 必须阻止发布

- 未知或不支持的协议版本；
- 重复 `publish_id`；
- 重复公开 slug；
- 非法枚举或缺少必需字段；
- `published` 与生成状态不一致；
- private、Daily、未授权草稿或 LLM 派生原稿进入公开结果；
- 本机绝对路径、`file://` 或私人 Vault 路径泄漏；
- 新 manifest 意外大量删除内容；
- 现有公开身份丢失；
- 需要重定向但没有提供映射；
- 输出目录位于真实知识来源内部。

### 可以形成 warning

- 未发布 Wikilink 被降级为纯文本；
- 可选 topic、series 或 kind 缺失并使用默认值；
- 来源文件移动但 `publish_id` 不变；
- 非关键资源缺失；
- 旧协议仍处于兼容期。

warning 必须进入 manifest，并在正式发布前人工确认。

## Manifest

manifest 从 Astro 同步报告演进为框架无关的发布对账记录，至少包含：

- 协议版本；
- 生成时间；
- 来源适配器和发布适配器标识；
- `publish_id`；
- 来源相对位置；
- 内容分类和输出语义；
- slug、最终 URL 和重定向；
- 状态与可见性；
- topic、series 和顺序；
- 内容和资源摘要指纹；
- warnings；
- 新增、修改、删除统计。

manifest 不包含私人正文，只保存足够完成对账、迁移验证和回滚判断的信息。

## 隐私与安全

- 来源适配器对真实 Vault 永远只读。
- GitHub Actions 不读取真实 Vault。
- BlogSite 不自动修改 `draft`、`published` 或私人内容。
- 网站不从 Daily 自动生成 NOW、成长记录或公开摘要。
- 私人路径、附件和本机配置不得进入仓库或报告。
- `managedBy: vault-sync` 的公开副本不得在 BlogSite 人工编辑。
- 手工网站内容和同步内容必须有明确 ownership，禁止同一 slug 双重管理。
- 来源路径允许变化，公开身份应保持稳定。
- Vault 来源目录只引用契约，不复制机器 schema 或完整枚举定义。

## 测试与验证

### 契约测试

- V1 必需字段和允许值；
- 可选字段默认行为；
- 未知协议版本；
- 重复 ID 和 slug；
- V1 到未来 V2 的兼容映射。

### 来源适配器测试

- 只使用合成 Vault fixture；
- 不读取真实 Vault；
- 文件移动但稳定身份不变；
- 目录结构变化；
- Wikilink 和资源转换；
- 同步前后来源文件哈希不变。

### 发布适配器测试

- 领域记录正确转换为 Astro 内容；
- draft、unlisted、public 行为；
- topic、series、kind 映射；
- RSS、搜索、详情页和长期主题；
- GitHub Pages 子路径；
- URL 和重定向。

### 端到端门禁

```text
preview sync
  -> 检查 manifest diff
  -> formal sync
  -> pnpm test
  -> pnpm check:publish
  -> pnpm build
  -> GitHub Actions
  -> live URL 验证
```

## 当前缺口

1. 发布协议分散在同步器、Astro schema 和多份文档中，没有单一权威契约目录。
2. Vault 发布模板、发布 MOC 和根级字段说明包含不完整的历史契约片段，容易被误认为权威模型。
3. 知识来源目录还没有一份只描述本地操作边界、并明确引用 BlogSite 权威契约的局部约定。
4. 当前正式 manifest 早于 `publish_kind` 实现，尚未反映新的生成字段。
5. `sourceVaultPath` 目前承担 provenance，但还没有稳定公开身份字段。
6. 当前同步流程把来源解析和 Astro 输出放在同一实现中，适配器边界不清晰。
7. 当前排除目录仍包含对现有 Vault 组织形式的知识。

## 分阶段实施建议

### 第一阶段：契约收敛

- 建立 BlogSite 内的发布协议 V1 文档和机器 schema；
- 明确字段归属、默认值和兼容规则；
- 在 Vault 实际发布来源目录写局部约定并引用权威契约；
- 不在 Vault 根级说明、发布 MOC 或模板中复制 schema、枚举和兼容逻辑；如需保留作者提示，只添加权威契约链接和最小使用说明；
- 由 BlogSite 契约、适配器和默认值处理 `publish_kind`，只在实际编辑相关公开稿时按需补值；
- 为现有公开内容建立身份基线；
- 重新执行 preview 和 formal manifest 对账。

### 第二阶段：代码解耦

- 从当前同步器中拆出 Obsidian 来源适配器；
- 建立框架无关领域记录和验证器；
- 将 Astro 输出拆成独立发布适配器；
- 保持现有正文、页面、slug 和 URL 不变。

### 第三阶段：迁移能力

只在真正准备重构时实施：

- 发布协议 V2；
- 双版本来源解析；
- 新旧 manifest 比较；
- 新旧网站并行构建；
- URL 重定向与回滚方案。

## 完成标准

设计实施完成后必须满足：

1. Vault 改目录不会自动破坏公开 URL。
2. BlogSite 改视觉或页面结构不会要求修改 Vault。
3. 新发布框架能通过新发布适配器消费相同领域记录。
4. 新知识来源能通过新来源适配器继续发布。
5. 发布字段变化有版本、默认值和兼容周期。
6. 所有契约模型只在 BlogSite 当前仓库维护。
7. 知识来源目录只保存局部遵守约定和契约引用。
8. 两个系统不会互相自动写入。
9. 每次正式发布都有可对账、可回滚的 manifest。
10. 同时迁移两端时可以分别验证和回滚。

# LeetCode C 语言训练：用算法题建立可验证的 C 实现习惯

这是一项正在进行的 C11 学习项目的公开说明，不是刷题日报，也不是一张等待勾完的题单。

我用算法题练习的不是“记住某个解法”，而是把一个看似成立的想法写成能经得起边界、内存和提交环境检验的 C 实现。算法给出明确的输入与复杂度约束，C 则迫使我说清数组边界、指针层级、返回值、资源所有权和失败路径。这两件事放在一起，才能暴露我原本以为已经懂了的地方。

## 我真正想练的能力

一道题的算法思路正确，并不意味着 C 实现已经可靠。我会反复检查这些问题：

- 输入为空、长度为零或边界刚好相等时，循环不变量是否仍然成立；
- 返回的数组、长度和二维结构分别由谁分配、谁释放；
- `qsort` 比较器、整数转换、指针解引用和提前返回是否留下未定义行为或资源泄漏；
- 本地测试通过后，提交源码是否仍能在平台提供的环境中独立编译；
- 验证结果到底来自官方样例、Sanitizer 还是线上判题，三者不能互相冒充。

## 项目怎样推进

项目内部始终只保留少量在手问题，任务真值和当天的停点留在私有项目记录与单题笔记中。公开页不复制“当前第几题”“今天完成了什么”之类会迅速过期的信息。

每轮练习至少需要经过自己的推导、官方样例和必要的 Sanitizer 检查；需要平台结论时，再以真实的线上回执为准。代码与测试继续以独立训练仓库为真值，公开文字只保留能解释设计判断的必要证据。

## 什么值得成为公开输出

不是每道完成的题都值得写成文章。只有当一次练习留下了可复用的判断时，我才会把它整理成独立的公开笔记或文章，例如：

- 一个看似正确的 C 写法为什么在边界、优先级或所有权上失败；
- 本地验证与线上提交环境为何不同，以及怎样让提交源码保持独立；
- 某个数据结构如何改变接口、清理责任或复杂度判断；
- 复习后我如何修正了第一次的思路。

这些输出应当从真实卡点、最小复现和验证结果长出来，而不是由题单、模板或自动生成的讲解替代。

## 这个项目不承担什么

- 不公开实时进度、每日学习时长或不断变化的当前工作集；
- 不把通用模板和资料摘要包装成个人结论；
- 不为了形成系列而为每道题写一篇复述题解；
- 不让写作任务挤占当前的独立思考与实现。

设计模式学习是另一项低优先级项目；它同样以实际问题和设计取舍为输出条件，而不是与本项目共同构成一条计划式阅读路线。

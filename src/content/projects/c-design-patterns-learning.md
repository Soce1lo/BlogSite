# C 语言设计模式学习计划

## 项目目标

这个项目以[卡码网设计模式编程课](https://kamacoder.com/course.php?course_id=14)的 23 种模式为概念主线，但不再要求使用 C 等权重完整实现全部题目。它是 [LeetCode C 语言训练计划](../leetcode-c-language-training/) 之后的低优先级副线，计划在 2026-09-15 前完成一次范围明确的闭环。

我希望完成四个层次的学习：

1. 能说清每个模式要解决的设计问题、关键角色和协作关系；
2. 能判断它什么时候有价值，什么时候只会增加复杂度；
3. 能先理解 Java、C++ 或 UML 中的标准面向对象表达，再判断是否值得转译为 C；
4. 对 9 种与 C 和嵌入式更相关的模式完成独立实现和验证，对其余模式给出最小替代方案或拒绝完整实现的理由。

## 为什么不再用 C 完整复刻 23 种模式

GoF 设计模式的常见讲解通常以类、继承、接口和虚方法为主要表达方式。C 缺少这些语言级构造，却仍然需要面对接口稳定性、行为替换、资源包装、对象协作和状态管理等设计问题。

如果要求 23 种模式全部用 C 搭出完整结构，学习时间很容易被手工函数表、伪继承和样板代码占据，反而模糊模式真正隔离的变化。因此新的学习顺序是：

1. 先理解标准面向对象表达中的角色和协作；
2. 再写出普通函数、`enum`、表驱动或直接组合构成的最小 C 方案；
3. 只有模式确实改善变化隔离、接口稳定性或生命周期管理时，才继续完成模式化 C 实现；
4. 如果最小方案已经足够，明确记录拒绝使用模式的理由。

拒绝过度设计也是本项目的正式学习成果，而不是“少做了一道题”。

## 优先级与截止日期

- **P1：[LeetCode C 语言训练计划](../leetcode-c-language-training/)**——当前 C 学习主线；
- **P2：本项目**——每周只使用 LeetCode 之外的 1–2 个剩余学习时段，不设置固定完成题数；
- **闭环日期：2026-09-15**——完成 23 种模式的概念判断、9 种重点模式的 C 验证和一次综合取舍记录；
- 如果进度落后，优先减少非重点模式的整理深度，不挤占 LeetCode 时间，也不降低重点实现的验证门槛。

## 重点 C 实作范围

以下 9 种模式进入完整的“标准表达 → 最小 C 方案 → 模式化 C 实现 → 样例与 Sanitizer → 复盘”闭环：

- 工厂方法：创建隔离与驱动选择；
- 适配器：接口兼容与硬件抽象层转换；
- 代理：访问控制、延迟访问或资源包装；
- 外观：为复杂子系统提供稳定入口；
- 观察者：事件通知与订阅者生命周期；
- 策略：算法或策略函数替换；
- 命令：请求封装、队列与撤销边界；
- 状态：显式状态机与状态相关行为；
- 责任链：处理流水线和分层决策。

其余 14 种模式先完成概念对照。只有实际问题显示它确实改善接口、变化隔离或资源管理时，才升级为完整 C 实作。

## 两种学习闭环

### 所有模式：概念对照

1. **识别问题**：先读题面，写下“不用这个模式时，哪个设计约束会被破坏”。
2. **理解标准表达**：阅读课程中的 Java、C++ 或 UML 结构，关闭页面后重述意图、角色、协作、适用场景和反例。
3. **写出最小 C 方案**：先尝试普通函数、`enum`、表驱动或直接组合，不默认引入函数表和动态多态。
4. **做出取舍**：说明模式化实现是否真的改善变化隔离、接口稳定性或生命周期；如果没有，记录拒绝理由后结束。

### 重点模式：C 实作

1. 明确 `struct`、组合、函数指针、上下文对象以及创建/销毁合同；
2. 独立完成 C11 标准输入/输出程序，再回看参考实现；
3. 运行页面样例、AddressSanitizer 与 UndefinedBehaviorSanitizer；
4. 记录一个实现错误、一个设计取舍和一个闭卷问题；
5. 完成 D+7 复习后才标记为“已闭环”。

## 完成标准

### 2026-09-15 项目闭环

- 23 种模式都有意图、适用场景、不适用场景和最小替代方案；
- 9 种重点模式都有可运行 C11 实现、页面样例和 Sanitizer 证据；
- 创建型、结构型和行为型各完成一次组内比较；
- 完成一个组合 2–3 种模式的小系统；
- 明确记录至少 2 个拒绝使用模式的决策及理由。

项目闭环不等于 23 道题全部在线 Accepted，也不要求发布 23 篇独立笔记。在线提交和 D+30 复习如发生则继续记录，但不作为 2026-09-15 的阻塞条件。

## 后续公开记录

9 种重点模式会逐步形成独立学习笔记；其余模式优先沉淀为创建型、结构型和行为型三篇组内比较。每篇公开记录都会回答：

- 这个模式隔离的变化是什么；
- 不使用模式时，最简单的实现是什么；
- 它在 C 中怎样通过结构体、组合、函数指针和生命周期表达；
- 实现时遇到了什么错误，怎样验证；
- 它与相近模式有什么区别，在哪些场景下不应该使用。

项目页维护路线、总体进度和模式索引；独立笔记保留真正值得复用的理解，而不是把每个课程条目都扩张成一篇文章。

## 课程收尾

概念对照和重点实作完成后，我不会用第 24 道孤立练习收尾，而会选择一个熟悉的小系统：

- 先画出不使用模式的最小设计；
- 选择 2–3 个真正有价值的模式完成组合设计；
- 明确拒绝至少 2 个不合适的模式，并记录理由；
- 用一页决策记录比较前后复杂度、可测试性和可扩展性。

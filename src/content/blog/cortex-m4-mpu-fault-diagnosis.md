# 从 MPU 配置到故障定位：一次 Cortex-M4 实践

我在一个 Cortex-M4 项目中完整配置并交付过 MPU。工作从整理内存区域和访问权限开始，随后用故意违规的访问检查配置，最后还暴露了供应商模块中的空指针解引用。供应商认可了问题，并承诺在后续版本修复。

这段经历让我把 MPU 配置和故障定位连在了一起：权限表规定什么访问可以发生，违规测试检查规则是否生效，异常现场则帮助解释到底是哪条指令越过了边界。只有把这些环节接起来，配置才能成为可检查的运行约束。

这里记录实践中已确认的经历，以及重新梳理时明确下来的诊断方法。当年的原始状态寄存器、完整指令现场尚未补入本文，供应商修复后的回归证据也仍缺失。因此，下面不会用一组假想日志填补真实案例。

## 先把内存用途变成访问规则

MPU 根据地址、访问类型和特权级，判断处理器的一次访问是否被允许。对当时的项目，我先按用途理解内存：代码需要取指，运行时数据需要读写，一些地址在当前策略下不应被访问。然后把这些要求转换成 Region 配置。

| 对象 | 当时的保护意图 | 对应违规测试 |
| --- | --- | --- |
| 代码区 | 可读、可执行、不可写 | 故意向代码区写入 |
| data/bss 所在数据区 | 可读、可写、不可执行 | 尝试跳入数据区执行 |
| 当前策略禁止访问的未覆盖区域 | 不允许该执行上下文访问 | 尝试读取 |

读、写、执行是需要分别判断的能力。“可执行”并不比“可写”更高一级，只读常量也不因此需要执行权限。若常量与代码共用一个 Region，实际权限还会受区域划分粒度限制；理想策略必须落到真正能表达的配置上。

项目只有 8 个可用 Region，无法给每一小段内存都分配一个。我使用了 Sub-Region，在有限条目内细化覆盖范围。这也使我开始关注链接布局和保护粒度之间的关系：链接脚本划出的边界，不一定恰好能由 MPU 描述。

Cortex-M4 这套 MPU 要求 Region 大小是 2 的幂，基地址按区域大小对齐；大小至少为 256 字节时，可以把区域分成 8 个等大的 Sub-Region，并通过 SRD 禁用其中一部分。禁用只表示地址不再命中这个 Region，不等于给该地址增加了一条禁止规则；它还可能命中其他重叠 Region。多个 Region 命中时，编号更高者优先。这些规则来自 [Arm Cortex-M4 通用用户指南的 MPU 章节](https://documentation-service.arm.com/static/5f2ac4ab60a93e65927bbdbf?token=)。

因此，配置检查需要看全部 Region 叠加后的结果，不能只看单行权限。8 个条目无法完整表达的细分策略，应保留为保护边界；交付了配置，也不意味着每个地址都获得了理想粒度的保护。

## “没有覆盖”需要带着上下文理解

当时的 `MPU_CTRL` 只置了 `ENABLE`，没有开启 `PRIVDEFENA` 和 `HFNMIENA`。这几个开关直接影响第三类测试的解释。

`PRIVDEFENA` 控制特权访问能否使用默认内存映射作为背景区。若它开启，特权访问没有命中显式 Region，也可能被背景区允许；背景区不会同样向非特权访问开放。所以“没配 Region 就一定不能访问”不是通用结论。测试前要明确执行模式、特权级、全部 Region 和控制位，并避开具有架构特殊规则的系统地址空间。

`HFNMIENA` 关系到 HardFault、NMI 及 `FAULTMASK=1` 时 MPU 是否生效。我的配置没有开启它，不能把普通执行路径中的保护结论直接套到这些上下文。控制位语义可对照 [CMSIS MPU 接口说明](https://arm-software.github.io/CMSIS_6/latest/Core/group__mpu__functions.html)。

这也限定了本文的讨论对象：这里验证的是该处理器核在给定上下文中的访问。DMA 或其他总线主设备是否受保护，需要另外检查芯片的总线与保护机制。

## 违规测试要证明哪一步

我做过的测试就是前面的三类：写代码区、执行 data/bss 区域、读取当前策略禁止的未覆盖区域。回头整理时，我意识到还应把“尝试了违规访问”与“证明 MPU 拦截了预期访问”分开记录。

第一步是确认测试指令真的存在并且执行到了。C 源码里的越界或非法访问可能涉及未定义行为；优化、内联和代码消除都会改变最后的指令。`volatile` 可以帮助保留某些访问，但不能单独证明测试有效，最终仍要核对反汇编和执行路径。

第二步是排除先发生的其他错误。向 Flash 代码区写入，可能先遇到存储器本身的写入限制；把普通数据当函数调用，又可能因目标不是合法 Thumb 指令或入口状态错误而失败。测试不可执行权限时，需要受控的、原本能够执行的指令内容与正确入口条件，才能区分执行权限拒绝和无效指令。对照组应保持访问目标及动作尽量一致，只改变待验证的权限条件。

第三步才是读取异常证据。系统停住、进入 HardFault，甚至重新启动，都不足以单独证明 MPU 生效。完整记录应把允许访问的对照、违规时的 Fault 状态和实际指令放在一起。这里是我对测试证据的整理要求，不表示当年的每一项对照记录已经齐全。

## 从“停住了”走到故障现场

MPU 访问违规通常由 MemManage Fault 报告。若该 Fault 没有使能，或优先级条件使其无法正常处理，可能升级为 HardFault。进入 HardFault Handler 后，仍应检查 `HFSR.FORCED` 与 `CFSR`，继续追查下层原因。相关规则见 [Arm 的 Fault handling and diagnosis](https://developer.arm.com/community/arm-community-blogs/b/embedded-and-microcontrollers-blog/posts/debugging-embedded-systems-part-2-fault-handling-and-diagnosis)。

定位时，我会先回答三个问题：发生了哪类错误，地址是否有效，保存的现场是否可信。`CFSR` 中的 `IACCVIOL` 与 `DACCVIOL` 分别提供取指和数据访问违规线索；使用 `MMFAR` 前必须看 `MMARVALID`，使用 `BFAR` 前必须看 `BFARVALID`。地址寄存器中有数值，不代表它就是本次有效故障地址。

随后才看异常栈帧。基本帧保存 R0–R3、R12、LR、PC 和 xPSR。帧内 LR 是被中断程序的返回线索；异常入口的 LR 则是特殊的 `EXC_RETURN`，用于判断返回上下文、MSP/PSP 选择及栈帧类型。进入普通 C 函数后再随意读取当前 LR、SP，可能已经读到处理函数自身的现场。

FPU 扩展帧、惰性保存、对齐以及压栈错误都可能影响解析。存在栈错误或二次 Fault 时，不能机械地把固定偏移上的数据当成 PC。对于非精确总线错误，异常报告还可能晚于肇事写操作，压栈 PC 也不能直接指认原始故障指令。异常入口与栈帧规则可查 [Cortex-M4 通用用户指南的异常模型章节](https://documentation-service.arm.com/static/5f2ac4ab60a93e65927bbdbf?token=)。

采集现场应尽量早，并避免先调用复杂日志代码。处理函数自身也需要可靠的栈和可访问的存储，否则可能在保存证据时再次故障。

## 低地址只是线索，指令才能连接到对象

严格保护配置生效后，项目暴露了供应商模块对低地址的访问。经过故障定位，确认是空指针解引用，供应商也认可了这一结论。这里的经验价值，是访问约束让原来隐藏的问题变成了可观察的异常。

但公开复盘不能让结论替代证据。低地址确实容易让人想到“空指针加成员偏移”，仍需把有效故障地址、故障指令和基址寄存器对起来。例如，假设一条加载指令使用某个寄存器加成员偏移寻址，就要用该现场中的寄存器值重新计算地址，再与有效地址记录比较。这个计算关系只是方法说明，不是当年的原始指令。

地址还必须使用故障发生时匹配的 ELF 解析，并结合反汇编检查。相近版本的 ELF 不够可靠，源码行号也可能受优化影响。固件版本、构建标识、编译选项、MAP、链接脚本和 Region 表，应随现场一起保存。只有回到具体指令，才能进一步判断哪个对象为空、对象为何未就绪、调用方与被调用方各自承担什么责任。

目前能够写下的事实是：问题已经定位并获得对方认可，对方承诺修复。尚不能写成“修复已验证”。后续仍需补齐原始状态位与指令现场，取得修复版本，在同一保护策略下复测原路径，留下可复核结果。

## 从这一段实践继续往下走

这次实践接起了配置、违规访问和故障定位，但异常发生之后，系统究竟如何保存现场、进入错误处理、停在循环中，或经主动复位、看门狗进入启动恢复，还需要沿真实代码继续理解。硬件异常本身不等于复位，软件栈检查失败也可能直接进入软件错误处理，并不一定先触发硬件异常。

我希望把后续的异常现场、栈保护、故障诊断和复位链路逐步补上。接触一点就先写下一点，回读时发现解释不清的地方，再带着问题去看材料和代码。这篇文章留下的原始现场与回归缺口，就是下一次学习可以接着走的地方。

# 多加了一次寄存器读取，为什么没改过的函数也变大了？

工作中遇到过这么一件事。我在一个周期任务里加了一次寄存器读取，重新编译后，固件大了不少。多一次调用，多几条指令，这很好理解。让我想不通的是，连初始化函数都变大了，而这次我根本没改它。

我和 Agent 在本机搭了个小实验，用 LLVM/LLD 22.1.8 给 Cortex-R52 编译 Thumb 代码，打开链接时优化（LTO）。原来那个产品用的是另一版工具链。这次没复现现场那么大的增量，倒是有 **2 个字节**，能在反汇编里认出是哪条指令。

## 调用加在周期任务里，多出来的指令却在初始化里

实验里，初始化函数 `mmio_init` 原本就会调一次 `mcal_read(0x10)`。这个接口收一个偏移，到外设基址加偏移的位置读寄存器。基线版本里已经有个周期任务，里面只更新心跳计数。先编一版，`mmio_init` 是 238 字节。

接着在周期任务里加一行，读另一个寄存器，把结果存下来。

```c
last_read = mcal_read(0x14u);
```

这时 `mmio_init` 变成了 240 字节。翻开它的反汇编，多出来的恰好是一条 2 字节的 Thumb 指令。

```asm
movs r0, #0x10
```

这条指令把初始化函数原本就要用的偏移放进参数寄存器 `r0`。可 C 源码一直写着 `mcal_read(0x10)`，为什么以前连这一步都能省？

## 保留新调用，只改它的偏移

要是直接删掉那一行，调用和新的偏移值会一起消失，还是分不出来究竟是哪件事影响了初始化。于是我把周期任务的读取留着，只将 `0x14u` 换成 `0x10u`，让两处调用读同一个寄存器。三版编出来是这样，表里都是字节数。

| 周期任务里的读取 | 初始化函数 | 周期任务 | 整个 `.text` |
| --- | ---: | ---: | ---: |
| 无 | 238 | 16 | 328 |
| `mcal_read(0x14u)` | 240 | 34 | 348 |
| `mcal_read(0x10u)` | 238 | 32 | 344 |

第三版的初始化函数回到了 238 字节，机器码和第一版逐字节相同。周期任务仍然会读寄存器，也仍然会保存读回来的值，所以整个代码段比第一版多了 16 字节。

答案在 LLVM 的中间表示（IR）里。打开 LTO 后，优化器能同时看见这两个调用点。一个传 `0x10`、另一个传 `0x14` 时，读哪个地址取决于这次收到的参数。两处都传 `0x10` 以后，在跨过程常量传播（IPSCCP）这一步，读取地址已经算成了常量。这时函数还带着形参。再看最终的 IR，内部函数已经变成 `@mcal_read()`，两个调用点都还在，都不用传偏移了。

回头再看表里的 348 和 344 就好算了。初始化里省掉一条 `movs r0, #0x10`，周期任务里省掉一条 `movs r0, #0x14`，各 2 字节。读寄存器的函数本身，两版都是 12 字节。

实验还给 `mcal_read` 标了 `noinline`。它的确一直是个独立函数，但 LTO 已经把它变成了内部函数，可以连同两个调用点一起改掉传参方式。地址固定下来以后，读动作也还在。最终的 IR 里能看到 `load volatile`，反汇编里能看到 `ldr`。编译器能算出地址，寄存器的值还是得在运行时取。

这些数字来自本地生成的 ELF，实验没有在板子上运行。产品里那次更大的增长，我还想拿改动前后的两份构建再看一次。我会先找到那个源码没动、尺寸却变了的函数，把两版反汇编摆在一起，看看它究竟多了哪条指令。

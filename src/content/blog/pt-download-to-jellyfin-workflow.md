# 从 PT 下载到 Jellyfin 入库：一套不破坏做种的动漫整理工作流

我使用 PT 下载动漫时，最初的流程并不复杂：qBittorrent 负责下载和做种，MoviePilot 负责把文件整理成 Jellyfin 能理解的目录结构，再由 Jellyfin 展示海报、季度和集数。

真正麻烦的是中间那一步。

许多动漫种子使用发布组自己的命名方式，标题里混着罗马音、季度、合集范围、压制参数和特殊篇标记。MoviePilot 一旦识别失败，我就要手动测试名称、增加识别词，再主动触发整理。自动化工具虽然都在，日常操作却依然停留在“下载完成后记得回来处理”。

我想改掉的正是这个断点，但前提比“能自动入库”更严格：不能移动或修改 qBittorrent 正在做种的原文件，不能让一次错误识别批量污染媒体库，也不能为了统一路径让已有种子重新校验甚至重新下载。

最后落地的方案是一条带安全门的自动流水线：只有明确打上标签的任务会进入 MoviePilot；识别通过后使用硬链接建立媒体库入口；Jellyfin 只读取整理后的目录。原始下载文件继续留在 qBittorrent 管理下，做种路径不变。

## 最终工作流

整个过程可以概括为：

```text
添加 PT 种子，并选择自动整理标签
                 |
                 v
       qBittorrent 下载与做种
                 |
         下载完成后发出通知
                 |
                 v
 MoviePilot 识别标题、媒体类型、季度与集数
                 |
       TMDB + 窄范围自定义识别词
                 |
                 v
 在媒体库目录创建硬链接、重命名并刮削
                 |
                 v
       Jellyfin 扫描并展示媒体
```

这里没有任何一步需要修改原视频内容。qBittorrent 管理下载副本与 PT 状态；MoviePilot 管理识别和媒体库目录；Jellyfin 只负责读取已经整理好的结果。三者的职责清楚后，自动化才不会反过来干扰做种。

## qBittorrent：原始文件和做种状态的唯一管理者

在这套流程里，qBittorrent 的下载目录始终是源数据。种子哈希、保存路径、完成状态、上传状态和站点规则都由 qBittorrent 维护，MoviePilot 不接管这些信息。

为了让后续自动化有明确边界，我没有让 MoviePilot 扫描所有已完成任务，而是使用一个专门标签：

- MoviePilot 发起的下载会自动带上标签；
- 手工添加 PT 种子时，只有主动选择该标签，任务完成后才会自动整理；
- 已经在做种的历史任务不补标签，因此不会被一次性重新处理；
- 没有标签的临时下载、测试任务和不希望入库的内容继续由 qBittorrent 单独管理。

标签在这里不是分类装饰，而是自动化的授权开关。它把“所有完成任务都可能被处理”收缩成“只有我明确选中的任务会被处理”。

## 共享路径：先统一新任务，不迁移旧种子

硬链接要求源文件和目标文件位于同一个文件系统。Docker 环境还多一层限制：qBittorrent 和 MoviePilot 不仅要看到同一份数据，还要对新任务使用一致的容器内路径。

我把目录关系收敛成一个共享媒体根目录：

```text
media-root/
├── download/    # qBittorrent 原始下载与做种
└── library/     # MoviePilot 整理后的媒体库入口
```

两个目录从同一个根目录挂进相关容器，避免把下载目录和媒体库分别映射成两个互不相干的 Docker 挂载点。这样 MoviePilot 才能在 `download/` 与 `library/` 之间创建真正的硬链接。

已有种子的路径迁移则采用兼容方式，而不是批量修改：

1. 保留 qBittorrent 原来的容器内下载路径，现有任务继续按原路径做种；
2. 额外挂载共享媒体根目录，让 qBittorrent 能看到 MoviePilot 使用的新路径；
3. 只把“以后新增任务”的默认保存目录切换到统一路径；
4. 不调用 qBittorrent 的位置迁移接口，也不离线修改恢复数据；
5. 重建容器前后逐项比较种子哈希、保存路径和内容路径。

这个顺序看起来保守，却把迁移风险限制在 Docker 配置层。旧任务没有移动，新任务自然进入新合同，两套路径可以在过渡期共存。

## 硬链接：一份内容，两个目录入口

整理完成后，下载目录和媒体库目录里会各出现一个文件名，但它们指向的是磁盘上的同一份数据。

这带来三个直接收益：

- MoviePilot 可以在媒体库一侧使用适合 Jellyfin 的文件名和目录结构；
- qBittorrent 一侧的原路径和文件名保持不变，继续校验与做种；
- 视频主体只占一份空间，不需要为媒体库再复制一份大文件。

硬链接也有容易误解的边界。重命名媒体库入口不会影响下载目录中的入口，但修改文件内容会同时改变两边看到的数据。删除其中一个入口不会立刻释放空间，只有最后一个硬链接也被删除后，磁盘空间才会真正回收。

因此，我把 MoviePilot 的整理方式固定为硬链接，不使用“移动”；同时把内容修改、清理下载目录和媒体库删除视为三类不同操作，不让 Jellyfin 目录承担种子生命周期管理。

## MoviePilot：识别、整理和刮削的编排层

qBittorrent 下载完成后，会调用 MoviePilot 的立即整理入口。MoviePilot 再检查标签、任务状态和下载路径，符合条件才继续识别。

一次成功整理通常包含这些动作：

1. 从种子标题中提取作品名、年份、媒体类型、季度和集数；
2. 查询 TMDB，确定稳定的媒体 ID 和元数据；
3. 根据动画电影、日番、国漫等分类规则选择媒体库目录；
4. 按 Jellyfin 友好的模板建立季度目录和文件名；
5. 创建硬链接，并生成海报、简介或其他刮削信息；
6. 让 Jellyfin 在整理后的媒体库中发现新内容。

MoviePilot、qBittorrent、Jellyfin 和代理服务运行在一个专用 Docker 网络中，服务之间使用容器名通信。这样重建容器后不需要依赖容易变化的内部 IP，也不用绕到宿主机端口再返回容器。

代理则只提供给确实需要访问外部元数据的服务。MoviePilot 通过显式代理访问 TMDB 和必要的代码源；qBittorrent 的下载与做种出口没有被代理接管，Jellyfin 的本地播放链路也不会绕过代理容器。这种做法比给整个 NAS 开透明代理更容易判断故障范围。

## 动漫识别：不要用一条大正则解决所有标题

基础链路稳定后，剩下的主要问题是动漫命名。

升级 MoviePilot 并恢复 TMDB 连通后，我先对现有动漫任务进行只读识别测试，没有立即开启自动整理。第一轮只有 25 个样本中的 17 个能正确命中；失败项主要是罗马音标题、发布组自定义简称、国漫英文名和剧场版别名。

我没有增加一条宽泛规则去删除所有方括号或画质参数，而是把内置识别放在自定义词表之前。规范的发布名通常已经足够让 MoviePilot 识别；只有预览确实失败、并且同类命名以后仍会重复出现时，才增加窄范围规则。必要时直接指定 TMDB ID、媒体类型和季度：

```text
\[发布组\]\s+作品英文名 => 作品标准名 {[tmdbid=987654;type=tv;s=1]}
```

像 `1080p`、`WEB-DL`、`中字`、`REPACK` 或裸露的 `S01E01` 都不适合作为全局规则锚点，因为它们会命中过多无关资源。发布组名前缀、罗马数字季度和 `PV`、`NCOP`、`NCED`、`Menu` 等特典标记也不应由一条全局正则处理。特殊篇、OVA 和跨季度合集必须单独校对集数，不与普通季度规则混在一起。

每次整理先在 MoviePilot 中只选正片文件做预览，确认标题、类型、季度、集数和目标路径；通过后才以 `link` 执行。只有预览失败时才写入词表，并再次预览同一原始文件。比如 `Chou Kaguya-hime! - Movie` 无法由内置检索命中，才补充指向 TMDB `1575337` 的电影规则；同目录的 `ray MV` 不匹配该规则，也不会被误入动画电影库。

实际回归验证表明，《为美好的世界献上爆焰！》12 集和《皇家国教骑士团 OVA》10 集都无需新增剧名规则即可完整识别，并以硬链接进入日番库。它们的下载源和媒体库入口设备号、inode、大小均一致，链接数至少为 2；Jellyfin 扫描后分别显示 12 集与 10 集。这个结果只代表当前样本，不意味着以后所有 PT 命名都能无条件识别。

更重要的收益是形成了一套安全增量方法：新标题失败时增加窄规则，并在全量回归通过后再进入自动整理。

## Jellyfin：只消费整理后的媒体库

Jellyfin 不直接读取 qBittorrent 的下载目录，而是只挂载 MoviePilot 整理后的媒体库。这样下载目录里复杂的发布名、合集结构、截图和校验文件不会直接出现在 Jellyfin 中。

媒体库按用途分开，例如：

- 动画电影；
- 日番；
- 国漫；
- 其他电影和电视剧分类。

MoviePilot 负责决定内容应进入哪个目录，Jellyfin 负责扫描、展示和播放。缺少媒体库时只补对应路径，不重建已有库，也不把一次配置修改变成全库迁移。

## 从手动整理到自动入库，效果如何

这次改造的价值不在于多运行了几个容器，而在于把原来需要记住的人工动作变成了可以验证的固定流程。

| 项目 | 改造前 | 改造后 |
| --- | --- | --- |
| 下载完成后的动作 | 记得回到 MoviePilot 手动触发 | qBittorrent 完成后立即通知 MoviePilot |
| 自动化范围 | 容易误扫全部完成任务 | 只有明确标签的任务进入整理 |
| 动漫识别样本 | 17 / 25 | 25 / 25，原成功项无 ID 漂移 |
| TMDB 访问 | 连接不稳定，识别链路会中断 | MoviePilot 使用隔离代理稳定访问 |
| 新任务路径 | qBittorrent 与 MoviePilot 路径语义不一致 | 新任务统一使用共享媒体根目录 |
| 历史任务 | 迁移可能触发移动或重新校验 | 哈希、保存路径和内容路径保持不变 |
| 媒体文件占用 | 复制会产生第二份视频 | 硬链接只保留一份内容数据 |
| Jellyfin 目录 | 分类不完整 | 动画电影、日番和国漫分别入库 |

为了确认“没有破坏做种”不是一句主观判断，我还做了两类验证。

第一类是 qBittorrent 状态对比：容器调整前后导出任务信息，比较所有种子哈希、保存路径、内容路径和未完成任务数量。结果保持一致，qBittorrent 本身也没有随着这次改造升级。

第二类是文件系统验证：从最近的整理历史中抽取三组源文件和媒体库文件，检查设备号、inode、文件大小和链接数。三组样本都指向同一个 inode，链接数不少于 2，证明媒体库入口确实是硬链接，而不是悄悄复制出来的第二份文件。

## 自动化仍然保留哪些安全边界

这条流水线可以自动运行，但不是无人值守地相信所有输入。

- 纯正片且批量预览全部正确的手工种子，才选择自动整理标签；
- 含 PV、CM、Menu、NCOP/NCED 或其他特典的整包不加自动整理标签，只在 MoviePilot 中选择正片文件手动预览和硬链接；
- 新识别词先只读预览，再写入窄范围规则；
- MoviePilot 只使用硬链接，不移动做种文件；
- 下载目录和媒体库必须位于同一文件系统；
- qBittorrent 的站点规则、分享率和删除策略仍由 qBittorrent 管理；
- 删除媒体库入口不会替代 qBittorrent 的种子清理流程；
- 特殊篇、合集和季度偏移仍可能需要人工确认；
- 容器重建前备份 qBittorrent 配置、MoviePilot 数据库和 Jellyfin 配置，失败时只恢复配置，不移动媒体数据。

如果以后出现误识别，最安全的处理方式不是直接改视频文件，而是先停用对应标签或监控，修正规则后重新整理媒体库入口。下载目录仍然保存着由 qBittorrent 管理的原始内容，可以作为稳定回退点。

## 这套流程最值得保留的部分

一开始，我以为问题只是“MoviePilot 为什么认不出某个动漫标题”。真正整理完之后才发现，识别率只是最后一公里。前面还有代理是否稳定、容器能否互相发现、两边路径是否一致、硬链接是否跨挂载、旧任务是否会被移动，以及自动化究竟被什么条件触发。

把这些问题一次拆开后，工作流变得很朴素：qBittorrent 保留原种，MoviePilot 只处理明确授权的任务，Jellyfin 只消费整理结果。遇到新命名时增加窄规则，遇到路径调整时只影响未来任务，所有高风险改动都用哈希、路径和 inode 复验。

现在我添加一个希望入库的 PT 种子，会先看它是否是纯正片任务：是的话可以在 qBittorrent 中选择自动整理标签；不是的话就在完成后只选正片文件预览，再让 MoviePilot 创建硬链接。两种路径都不移动原文件，Jellyfin 只读取整理后的入口，原文件继续留在原位置做种。

这正是我希望家庭影音自动化达到的状态：平时不需要惦记它，出问题时知道每一层负责什么，也始终保留不会伤到原始数据的退路。

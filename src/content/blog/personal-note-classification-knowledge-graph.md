# 我的个人笔记如何分类：从个人信息管理研究到知识图谱

> **我的选择**
>
> 我不再尝试用一棵目录树或一组标签解释所有笔记，而是让目录、页面类型、成熟状态、主题标签、对象类别、双链关系和 MOC 分别回答不同的问题。人物、书籍、电影、组织、活动和任务可以逐渐成为节点，但只有产生有效内容时才建立页面。未来如果需要知识图谱，结构化数据也应从 Markdown 派生，而不是反过来支配今天的记录。

专题总览：[我的个人知识系统](../obsidian-personal-knowledge-management-skill/)。

## 这个问题是怎样出现的

当 Daily 里开始出现人物链接，以及书籍、电影、活动和任务等不同对象时，一个看似简单的问题出现了：它们究竟应该怎样分类？

最直觉的办法，是为人物、书籍、电影和活动各建一个标签或目录。这样短期内很整齐，却会迅速遇到边界问题：一本书既是作品，也是信息来源；一场课程既是活动，也可能留下可引用的资料；一个任务可能只是今天的下一步，也可能逐渐发展成项目。人物与组织的关系还会随时间变化，无法由一个永久标签完整表达。

我真正想建立的也不只是一套文件收纳规则。我希望个人笔记将来能够承载家庭、亲密关系、同事协作和组织层级，形成以自己为中心的关系网络；同时，Daily 仍然应该保持低摩擦，不因为一个新名字或新概念出现，就被迫立刻填写一套复杂元数据。

因此，这次调研关注的不是“哪一种分类法最流行”，而是三个更基础的问题：人们实际上怎样保存和找回个人信息？成熟分类学怎样处理一个对象同时属于多个维度？如果未来需要知识图谱，今天应该保留哪些结构，又不必提前承担本体和数据库的维护成本？

## 从个人信息管理研究得到的第一条结论：目录没有过时

William Jones 对个人信息管理的综述把问题放在完整生命周期中讨论：信息会被获取、组织、维护、找回和使用。分类的价值不在于保存时看起来整齐，而在于未来能否在某个任务、角色或问题中重新找到它。[Jones 与 Teevan 的 PIM 研究](https://uwapress.uw.edu/book/9780295987552/personal-information-management/)也提醒我，个人信息天然与行动语境和长期目标相连。

关于文件夹和标签的实证研究并没有得出“标签应该取代目录”的结论。[Civan 等人的比较](https://doi.org/10.1002/meet.2008.1450450214)显示两者各有优势，给同一信息附加多个标签还会增加操作成本；[Bergman 等人的研究](https://doi.org/10.1002/asi.22906)则观察到参与者仍然明显偏好文件夹。

这使我保留了当前 Vault 的物理分层：Daily 是原始输入，Inbox 是已经被识别但尚未稳定的概念，Notes 保存长期理解，Projects 承担交付，Areas 表达持续职责，Resources 保存外部材料，MOCs 负责导航。它们首先回答的是“这份内容现在承担什么职责”，而不是“它在世界上属于哪一种实体”。

这也解释了为什么 知识管道 的核心不是把一切尽快分类，而是让原始输入、孵化、研究缓存和正式知识拥有不同的提升门槛。

## 从分面分类得到的第二条结论：不要让一个维度承担所有语义

图书情报学中的分面分类给出了更关键的启发：一个对象可以从多个相互独立的角度被描述，单一层级很难容纳这些角度。[Microsoft Research 对分面搜索的总结](https://www.microsoft.com/en-us/research/publication/faceted-search/)指出，多分面可以克服单一结构的限制，但分面越多，界面和维护成本也越高。

这正好解释了我原先感到混乱的原因：我曾试图让目录、`type` 和标签同时回答“这是什么”。事实上，它们应该各自回答不同问题。

| 分面 | 它回答的问题 | 在我的 Vault 中的表达 |
| --- | --- | --- |
| 物理去向 | 内容当前由哪一层负责？ | Daily、Inbox、Notes、Projects、Resources、MOCs 等目录 |
| 页面职责 | 这篇页面在系统里做什么？ | `type`，例如 `note`、`resource`、`project`、`moc` |
| 生命周期 | 它目前成熟或运行到什么阶段？ | `status` |
| 主题 | 它涉及哪些跨领域话题？ | 主题标签 |
| 对象类别 | 当前谈论的是谁或什么？ | 人物、组织、作品、事件等候选词表 |
| 关系语境 | 它与其他对象怎样相关？ | Wikilink 周围的自然语言与反向链接 |
| 导航视角 | 我想围绕什么问题阅读这些内容？ | MOC、Base 和搜索 |

这种拆分让我不再追求“唯一正确位置”。一本关于组织设计的书可以物理上位于 Resources，页面职责是 `resource`，状态是 `growing`，主题是知识管理和组织设计，同时被不同 MOC 引用。每个维度都提供信息，但没有一个维度需要吞掉其他维度。

## Zettelkasten、PARA 和 MOC 并不是竞争关系

调研中另一个重要发现，是许多著名方法实际上解决的是不同问题。

[Luhmann 的卡片盒](https://niklas-luhmann-archiv.de/nachlass/zettelkasten)依靠可寻址卡片、索引和交叉引用形成工作网络。它启发我把链接视为关系和发现工具，而不是只把笔记塞进主题树。[PARA](https://fortelabs.com/blog/para/)按照项目、领域、资源和归档组织材料，更接近“我现在准备拿它做什么”。[MOC](https://blog.linkingyourthinking.com/maps/)则是一种人工策展的导航页，适合围绕一个问题组织阅读入口。

它们无需互相取代：PARA 类目录提供行动语境，Zettelkasten 类链接连接可寻址思想和对象，MOC 提供阶段性的阅读结构。更重要的是，目前没有可靠的对照研究证明其中任何一种方法能够单独、普遍地提高长期知识产出。因此，我选择吸收它们各自有用的部分，而不把某个作者的方法当成必须完整复制的教条。

## 我最终采用的对象分类

在目录、页面职责和主题已经分开的前提下，我仍然需要一套足够基础的词汇，帮助识别新出现的对象。最终接受的候选分类有九类：

| 类别 | 主要覆盖范围 |
| --- | --- |
| 概念 | 观点、问题、方法、术语和可继续发展的理解 |
| 人物 | 家人、朋友、同事、作者和公共人物 |
| 组织 | 公司、部门、团队、社区和机构 |
| 地点 | 城市、场所、驻地和具有持续语境的空间 |
| 作品或人工物 | 书、电影、软件、设备、产品和艺术作品 |
| 来源或文档 | 文章、论文、网页、课程、访谈、数据集和文件 |
| 事件或活动 | 对话、会议、聚会、旅行、体验和里程碑 |
| 项目 | 有目标、交付物和结束条件的连续行动 |
| 任务或行动项 | 可以执行和完成的下一步 |

这九类不是九种 `type`，也不是必须互斥的本体。一部电影作为被观看和评价的对象时更接近“作品”，作为分析论据时又承担“来源”的角色；一门课程既可能是活动，也可能产生资源。我的处理原则是根据当前内容的用途选择一个主类别，必要时保留一个次要观察，但不因此复制页面。

“项目”和“任务”也体现了这种语境性。任务描述下一步，项目描述由多步行动构成的交付目标；只有项目真正形成页面时，`type: project` 才表达那篇页面的职责。现实对象类别与笔记页面类型有关联，但不是同一回事。

## 双链先表达可能性，页面等待有效内容

Wikilink 在这套系统中最重要的价值，是允许一个节点先被指出，而不要求它立即拥有完整页面。一个名字第一次出现在 Daily 中时，链接已经记录了“这里可能存在一个值得追踪的对象”；以后出现更多上下文，反向链接会自然聚合这些痕迹。

因此，未解析链接不是错误，而是一种尚未决定是否落盘的状态。人物、组织、书籍或活动只有在形成可复用的关系背景、判断、摘要、来源记录或多次上下文后，才值得拥有独立页面。空页面只会制造分类完成的错觉，并不会增加知识。

MOC 也遵循同一逻辑。它不是按“人物大全”“书籍大全”预建的总目录，而是在某个问题已经稳定时出现的阅读地图。一个个人社会关系 MOC，未来可以围绕家庭、亲密关系、公司协作和组织层级展开；它的价值来自真实内容之间已经存在的联系，而不是提前搭好的空架子。

## 为什么现在不直接建立知识图谱

[个人知识图谱研究](https://doi.org/10.1145/3341981.3344241)把 PKG 定义为与个人相关的实体、属性和关系。它与我的设想非常接近：许多重要人物和对象并不具有公共知名度，却对个人生活和决策十分重要。[2024 年的 PKG 生态综述](https://doi.org/10.1016/j.aiopen.2024.01.003)进一步把数据所有权、访问控制、互操作和隐私放在核心位置。

但知识图谱并不只是把 Obsidian Graph view 画得更漂亮。真正可查询的关系需要稳定身份、明确方向和关系类型；现实中的角色与隶属关系还需要时间、来源和隐私边界。[W3C Organization Ontology](https://www.w3.org/TR/vocab-org/)把人物、组织单元、成员关系和角色分开，正是因为“某人在某个时期以某种角色属于某个部门”不能被一个静态标签准确表示。

如果未来确实需要查询个人关系网络，更合适的模型会接近：

```text
人物 ── 成员关系 ── 组织单元 ── 隶属于 ── 组织
          │
          ├── 角色
          ├── 有效时间
          ├── 来源
          └── 隐私与置信说明
```

今天先把这些关系写在链接周围的自然语言中，反而更准确，也更容易修订。等到出现稳定查询需求时，再从 Markdown 派生结构化图谱，逐步增加稳定 ID、关系词表、时间和出处。RDF、JSON-LD、SKOS、PROV-O 或 OWL-Time 都可以成为将来的交换与表达工具，但没有必要提前成为日常写作负担。

我的原则是：**Markdown 保存人工可读的知识真值，知识图谱是可以重新生成的投影。** 这样即使未来更换工具或数据库，今天写下的内容仍然完整、可读，也不会被某个产品的私有模型锁定。

## 这套分类方式刻意没有做什么

我最终放弃了三种看起来整齐、实际上容易产生长期负担的做法。

第一，不把 `person`、`book`、`movie` 等现实对象类别写进 `type`。`type` 服务的是页面职责，不是世界本体。

第二，不用“人物、书籍、电影、活动”标签建立第二套隐藏 Schema。标签继续表达知识管理、组织设计、嵌入式等主题，状态也继续由 `status` 表达。

第三，不因为一个 Wikilink 出现就自动创建页面，也不预建九个实体总 MOC。分类能力可以先存在，页面和导航等有效内容涌现后再出现。

这使当前系统保持轻量：Daily 仍然可以直接写，Obsidian 任务管理工作流 继续把任务保留在产生它的上下文中，知识分类则在需要检索、连接和沉淀时逐渐显现。

## 结语：今天保持简单，明天仍然可以计算

这次调研最终没有为我找到一套需要照搬的标准答案，而是帮助我明确了分类的边界。

目录保存稳定的职责语境，`type` 和 `status` 描述页面，标签提供主题切面，Wikilink 表达对象与关系，MOC 组织问题，九类候选词表帮助识别新对象。它们组合起来，比一棵越来越复杂的分类树更能容纳真实生活中的模糊、变化和交叉。

对我而言，前瞻性并不意味着现在就部署图数据库，而是让今天的简单记录不阻断明天的结构化可能：节点可以逐渐形成，关系可以以后增加时间和出处，Markdown 可以继续作为人的知识，而图谱在真正有价值时再成为机器的视角。

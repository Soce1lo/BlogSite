# 用 Obsidian 管理任务：Daily、看板与项目进度的职责分离

我曾经把任务查询、日常入口、任务写法和复盘说明都堆在一个 Obsidian 工作台里。它最初很方便：打开一页，就能看到今天、本周、未排期和最近完成的任务。但任务一多，问题也开始集中出现。

电脑右侧栏放不下长标题和日期，手机侧栏又不适合复杂操作；“计划开始”和“真实截止”混在同一个时间查询里，同一任务会进入多个区间；没有日期的任务则把项目 backlog、知识清单和真正待办混在一起。

后来我没有继续给工作台叠查询，而是把任务系统拆成了几个职责明确的部分：

- Daily 是每天进入和收口的地方；
- Markdown task 是唯一任务真值；
- Tasks 负责解析、日期和跨笔记查询；
- Task List Kanban 负责电脑端规划、改期与状态切换；
- Bases 负责项目状态；
- Weekly 负责复盘和下一周期选择。

这套方法的关键不是安装了哪些插件，而是让任务、视图和项目进度不再互相冒充。

## 任务应该留在上下文中

看板很容易让人产生一种冲动：把所有任务都搬进去，建立一份独立任务数据库。这样做的代价是，任务和产生它的上下文分开了。

一个“验证通信异常恢复”的任务，可能来自某个项目的实验记录；一个“补充文章引用”的任务，可能来自某篇正在写的稿件。如果任务只剩一行标题，过几天再看时往往不知道为什么要做、做到什么程度。

所以我的做法是：

- 当天产生、一次性的行动写在 Daily；
- 围绕明确交付物、需要跨天推进的行动写在项目笔记；
- 真正需要长期重复的职责才放在 Area；
- 知识检查清单、参考目录和“以后可能做”的想法继续使用普通列表。

只有已经决定执行的行动才写成 `- [ ]`。看板从这些源笔记读取任务，也把状态和日期修改写回源笔记。它是操作界面，不是第二份数据。

## 用四种状态表达任务生命周期

我只保留四种通用状态：

| 状态 | Markdown | 含义 |
| --- | --- | --- |
| Backlog | `[ ]` | 已经确认要做，但尚未开始 |
| Doing | `[/]` | 当前正在推进 |
| Done | `[x]` | 已完成 |
| Cancelled | `[-]` | 已明确取消 |

状态不使用标签表达。标签适合描述主题，不适合承担任务生命周期。

在电脑看板中，任务按照 Backlog → Doing → Done 推进。简单任务如果是在 Daily 或手机上直接完成，也可以从 `[ ]` 直接勾选为 `[x]`。两种方式都修改同一条 Markdown task。

## 把计划日和截止日分开

任务系统里另一个常见问题，是把所有日期都当成 deadline。结果是每天为了“重新安排任务”不断修改截止日，最后真正的承诺日期失去了意义。

我使用的日期语义是：

- `⏳ scheduled`：计划实际处理的日期；
- `📅 due`：真实截止日期；
- `🛫 start`：在此之前不准备开始；
- `✅ done`：实际完成日期。

日常规划主要使用 scheduled。只有存在外部期限、明确承诺或真实后果时，才填写 due。

```md
- [ ] 整理实验结果 ⏳ 2026-07-28
- [ ] 提交项目报告 ⏳ 2026-07-29 📅 2026-07-31
```

计划变化时调整 `⏳`，不要为了让任务出现在今天而修改 `📅`。

## 打开 Obsidian 后先进入 Daily

我的 Obsidian 启动后直接打开当天 Daily。页面顶部只有两组任务查询：

1. 今天需要处理或已经逾期的任务；
2. 未来七天有 scheduled 或 due 的任务。

它们使用完整显示模式，日期直接可见，手机上也不需要依赖鼠标悬浮。

每天开始时，我先浏览这两组任务，再在“今日重点”写下今天真正想推进的 1～3 件事。新产生的一次性行动写在“下一步”；属于项目的行动回到项目笔记记录。

Daily 不负责保存所有项目任务。它只回答三个问题：

- 今天最重要的是什么；
- 今天实际发生了什么；
- 下一步是什么。

## 电脑端用看板做规划和改期

需要集中规划时，我在主编辑区打开 Task List Kanban，而不是把它塞进右侧栏。

看板按源文件分组。每个 Daily 或项目笔记形成一个任务泳道，可以直接看出任务来自哪里。卡片展示 scheduled、due 和 priority，并保留打开源文件的入口。

我的操作顺序通常是：

1. 切换到按计划日或按截止日排序；
2. 检查逾期任务是否仍然有效；
3. 从 Backlog 中选择准备开始的任务；
4. 推进到 Doing；
5. 必要时修改 scheduled 或 due；
6. 完成后推进到 Done。

完成和取消的任务默认不显示。这样可以避免大量历史任务生成空泳道，也让看板保持为“当前行动面”，而不是完成记录档案。

看板同一时刻只使用一种排序。我保留默认优先级排序，同时保存“按计划日”和“按截止日”两个视图。需要多级排序时，交给 Daily 中的 Tasks 查询。

## 手机只承担轻操作

手机端没有必要复制电脑上的完整看板。打开今日 Daily 已经足够：

- 查看今天、逾期和未来七天；
- 勾选完成；
- 快速写下一条行动；
- 打开来源笔记补充少量上下文。

任务拆分、批量改期、状态拖拽、项目复盘继续在电脑完成。设备分工之后，手机界面更简单，也减少了为了适配移动端而牺牲电脑效率的情况。

## 项目进度不要等同于任务百分比

任务状态和项目状态是两件事。

我用 Obsidian Bases 建立项目总览，只显示 active 或 paused 项目，并展示最近更新时间。进入项目笔记后，再查看目标、行动、日志和交付结果。

我没有给项目维护手工完成百分比。任务可以随时拆分、合并或取消，百分比很容易产生虚假精确感。判断项目是否真的前进，更可靠的依据是：

- 项目状态有没有变化；
- 最近是否更新；
- 是否完成了真实行动；
- 是否产生可核对的交付物。

专项学习进度可以继续使用自己的状态模型，不必强行塞进通用项目百分比。

## Daily 负责收口，Weekly 负责选择

每天结束时，我回到 Daily 做一个很轻的收口：

1. 写一句实际结果或决定；
2. 检查 Doing 是否还有未完成任务；
3. 为继续推进的任务决定下一次 scheduled；
4. 不再需要的任务明确取消；
5. 留下一条明天可以直接开始的下一步。

Weekly 不承担实时任务列表，而是处理更高一层的问题：

- 本周完成了哪些可核对的事实；
- 哪些项目状态发生变化；
- 哪些任务长期没有排期；
- 哪些任务应该取消；
- 下周真正要推进的少数事项是什么。

完成记录留在源 Markdown 中，Weekly 再从这些事实中做选择。看板不需要长期展示一个越来越大的 Done 列。

## 实施时最容易忽略的边界

这套工作流落地后，有几条经验值得保留。

第一，任务来源一定要收窄。正式知识笔记、资源、发布稿、模板和历史归档中的 checkbox 很可能只是示例或检查清单，不应该进入日常任务看板。

第二，Markdown 中的数字 checkbox 形式有时会被插件识别为任务状态，例如参考文献里的 `[1]`。如果笔记中存在这类写法，需要在看板中明确忽略数字状态。

第三，隐藏 Done 不一定足够。有些看板仍会因为历史完成任务创建空的源文件分组，需要同时排除完成状态，才能让界面真正收敛到当前行动。

第四，任何插件操作都应该验证是否回写源文件。我分别测试了状态推进和日期修改，确认最终变化落在原 Markdown task 上，再把看板视为可靠操作入口。

## 一条足够简单的日常路径

最后，这套系统可以压缩成一条很短的使用路径：

> 打开 Daily 看今天 → 去看板选择任务并切到 Doing → 回源笔记工作 → 完成后切到 Done → 晚上在 Daily 留结果和下一步 → Weekly 再决定下一周期。

任务管理没有脱离知识管理。任务仍然和项目、笔记、实验、写作上下文放在一起；视图只帮助我在合适的设备上看到合适的切面。

这比维护一份独立而完整的任务数据库更克制，也更符合我使用 Obsidian 的原因：知识和行动都保存在可读、可链接、可追溯的本地文本中。

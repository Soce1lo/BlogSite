# C语言专业编程技巧清单

## 使用场景

这份清单不是“C 语法小抄”，而是从高质量资料里提炼出的写 C 代码的工作习惯。考试时重点看“可以减少失误、便于验证、容易被阅卷或代码审查理解”的技巧；工程中再按项目约束选择更严格的安全规则。

参考资料包括 C语言专业级考试参考资料 中的 Princeton COS217 风格规则、NASA C Style Guide、Power of Ten、Modern C、comp.lang.c FAQ、Harvard CS61 内存材料和 Linux kernel coding style。

## 先让代码可机械检查

### 技巧

- 从第一天就启用足够严格的警告，并把新增警告当成错误处理。
- 把“容易写错”的约束写成断言、边界检查或小工具函数，而不是留在脑子里。
- 对内存和未定义行为使用 ASan/UBSan；对复杂项目再加静态分析。

### 考试落地

- 本地练习默认用 `-Wall -Wextra -Wpedantic -Wconversion -Wshadow`。
- 最后提交前至少跑一次最大输入、空输入和退化输入。
- 不能把 sanitizer 无报错当作正确性证明；它只证明这次运行没触发它能检测到的错误。

## 控制流要简单

### 技巧

- 一个表达式只做一件有副作用的事。
- 避免把多个赋值、递增和函数调用压到一行里。
- 循环边界写成容易审查的形式，能用半开区间就保持一致。
- 安全关键代码会进一步要求限制递归、限制无界循环和限制复杂控制流；考试代码不必完全照搬，但要理解其目标是“让人和工具都能证明它会停、会释放资源、不会走隐藏路径”。

### 考试落地

```c
/* 好：边界和副作用分开 */
while (left < right) {
    size_t mid = left + (right - left) / 2;
    if (a[mid] < target) {
        left = mid + 1;
    } else {
        right = mid;
    }
}
```

不要写成：

```c
/* 坏：把边界、更新和副作用揉在一起，不利于审查 */
while (l < r && a[m = (l + r) / 2] < x) l = ++m;
```

## 函数保持小而有明确目的

### 技巧

- 函数只做一件事，并让名字描述动作。
- 局部变量越多，通常越说明函数边界不清晰。
- 需要注释解释一大段控制流时，先考虑拆函数或改结构。

### 考试落地

- 把 `lower_bound`、堆操作、并查集、解析函数写成独立小函数。
- 主函数只做读入、调度和输出。
- 复杂 DP 可以把“初始化”“转移”“答案提取”分成三个清晰块。

## 命名服务于作用域

### 技巧

- 全局对象和跨模块函数必须用描述性名字。
- 局部短循环变量可以短，但作用域要小。
- 名字必须准确，不要用 `count` 表示容量、用 `size` 表示最后下标。

### 考试落地

- `n`、`i`、`j` 可以用于短循环。
- 图题里区分 `vertex_count`、`edge_count`、`capacity`。
- 动态数组里区分 `size` 和 `capacity`，不要用同一个变量承担两种语义。

## 资源在哪层申请，就在哪层释放

### 技巧

- 分配者和释放者必须在接口上说清楚。
- 同一函数内有多个失败出口时，用统一清理路径减少遗漏。
- 清理标签命名要说明清理动作，不要只写 `err1`、`err2`。

### 考试落地

```c
int rc = EXIT_FAILURE;
int *a = NULL;
long long *prefix = NULL;

a = malloc(n * sizeof *a);
if (a == NULL && n != 0) {
    goto cleanup;
}

prefix = calloc(n + 1, sizeof *prefix);
if (prefix == NULL) {
    goto cleanup;
}

rc = EXIT_SUCCESS;

cleanup:
free(prefix);
free(a);
return rc;
```

如果后续新增资源，先补清理路径，再写中间逻辑。

## 动态内存遵守一次分配、一次释放

### 技巧

- `malloc` 返回的存储未初始化。
- `free` 的参数必须是空指针或仍然活跃的动态分配块起始地址。
- `calloc(count, size)` 也要考虑元素数和元素大小是否来自可信范围。
- `realloc` 成功后只使用新指针；失败时原对象仍有效。

### 考试落地

- 保存 `realloc` 返回值到临时指针。
- 数组分配前检查 `count > SIZE_MAX / sizeof *p`。
- 结构体内含指针时，先定义清楚深拷贝、浅拷贝和销毁责任。

## 宏要少，且必须像语法单元

### 技巧

- 能用 `static inline` 函数就不用函数式宏。
- 宏参数和宏整体都加括号。
- 多语句宏使用 `do { ... } while (0)`。
- 宏不要隐藏指针解引用、控制流跳转或多次求值。

### 考试落地

```c
#define ARRAY_LEN(a) (sizeof(a) / sizeof((a)[0]))
```

这个宏只能用于真实数组对象，不能用于指针形参。把它用于函数参数中的“数组”通常是错误。

## 用语言计算大小，不手写魔法数字

### 技巧

- 分配和拷贝时用 `sizeof *ptr`，避免类型改了但大小没改。
- 常量要有名字，并尽量靠近它服务的约束。
- 字符串缓冲区要明确容量是否包含终止符。

### 考试落地

```c
int *values = malloc(count * sizeof *values);
char word[32];
scanf("%31s", word);
```

`31` 的来源是 `sizeof word - 1`。如果不是固定格式输入，优先用 `fgets` 后解析。

## 接口要小而正交

### 技巧

- 一个模块暴露少量互相独立的基本操作，比暴露大量交叉接口更可靠。
- 不要让调用者绕过接口直接改内部状态。
- 函数参数要表达前置条件，非空、容量、长度、所有权都要能从名字或注释看出来。

### 考试落地

- 堆只暴露 `push`、`pop`、`free` 这类基本操作。
- 并查集只暴露 `find`、`union`，外部不要直接改 `parent`。
- 字符串处理函数总是带上容量或长度。

## 注释解释不变量，不重复代码

### 技巧

- 不要把显然的赋值翻译成中文注释。
- 注释应该说明区间约定、所有权、复杂度、错误处理和为什么这样写。
- 如果注释在替代码道歉，先重写代码。

### 考试落地

好注释：

```c
/* prefix[i] is the sum of a[0..i). */
```

坏注释：

```c
/* i 加一 */
++i;
```

## 指针层级要克制

### 技巧

- 指针本身已经很难审查，不要用 typedef 或宏把指针隐藏起来。
- 能用数组下标表达的线性访问，不必强行写成复杂指针算术。
- 对外接口尽量避免多级指针，除非它明确表示“函数要修改调用方指针”。

### 考试落地

- `struct Node *next` 比 `NodePtr next` 更容易看出对象关系。
- `int **matrix` 与平坦数组 `int *data` 的内存模型完全不同，不要混用。
- 修改动态数组容量时用 `int **out` 或返回新指针，并明确失败时原指针是否仍有效。

## 不要把平台风格误当 ISO C 规则

### 技巧

- Linux kernel coding style 很适合学习可维护系统 C 的经验，但其中很多规则服务于内核生态，不是 ISO C 标准。
- NASA/Power of Ten 面向安全关键场景，约束比普通考试严格。
- Modern C 会覆盖 C23，考试环境未说明时不要默认可用。

### 考试落地

- 资料中学“为什么要降低复杂度、减少隐藏状态、强化检查”，不要盲目照搬所有缩进、命名或禁止项。
- 答题默认使用题目声明的 C 标准和编译器，不因资料新就使用新语法。

## 复盘时按缺陷类型归档

每次练习后把错误归到固定类别：

- 类型和转换。
- 下标和区间。
- 输入解析。
- 所有权和释放。
- 算法复杂度。
- 初始化和哨兵。
- 格式化输出。
- 题意误读。

这样比简单记录“这题错了”更有复用价值。

## 资料映射

- Princeton COS217 / The Practice of Programming：命名、表达式、宏、资源层次、接口和注释。
- NASA C Style Guide：C 工程风格、推荐实践和常见 C 问题处理。
- Power of Ten：可验证性、简单控制流、断言、静态分析和警告零容忍。
- Modern C：现代 C 标准、C23 边界和更系统的语言模型。
- comp.lang.c FAQ：常见 C 误解、数组指针、预处理器、内存和字符串问题。
- Harvard CS61：动态内存分配、活跃对象、非法释放和边界场景。
- Linux kernel coding style：可维护 C 的函数拆分、命名、错误清理路径和避免隐藏复杂度。
